# M7 status — C64 via TRX64 (S14)

Milestone M7, first part (docs/specs/S14-c64-trx64.md). **Phase A reached.** The unmodified firmware (`ultimate.elf`,
V1.01 3.15) resets, stops and resumes a TRX64 C64, uploads its ROMs, reads and writes its bus through the DMA window,
starts the boot cartridge to run a PRG from the file browser, and draws the Freeze UI on its screen. The C64 frame
appears under the overlay in the window and in PNGs.

`--c64 trx64` is the default when ue2emu is built with its default `trx64` feature; `--c64 none` is the T0 register
stub of before. `cargo build -p ue2emu --no-default-features` builds without TRX64 and without a C++ toolchain.

## Phase B (wave 4, merged)

Three streams, merged into `main` in this order (S14 §W4-SID, §W4-CART, §W4-DRIVE):

| Stream | What works | Status |
|---|---|---|
| W4-SID | An ARMSID in socket 1 (`--sid-socket1 armsid`), detected and enabled by the firmware; socket 1 and UltiSID 1 on TRX64's reSID; DMA reads of the SID range; audio through cpal (`--audio`) and into a WAV (`--audio-wav`) | `docs/status/sid-audio.md` |
| W4-CART | all_carts_v5.vhd on guest DDR: 27 cartridge types from the file browser, the Action Replay freeze (USB F11), the GMOD2 EEPROM, EasyFlash writes kept over reset and saved, the SID and MUS players | `docs/status/carts.md` |
| W4-DRIVE | Drive A as a 1541 on TRX64's drive 8 behind the firmware's drive registers: directory, LOAD and SAVE on a mounted D64, written tracks back in the image | `docs/status/drive.md` |

Merge notes (beyond keeping both sides):
- `Trx64Backend::run_cpu` (CART) passes the SID tap (SID) to every TRX64 run: plain runs use `SidTap`, cartridge runs
  a `CartObserver` that forwards `on_bus` to it. Otherwise the SID writes of a program running under a cartridge (the
  SID player) would not reach reSID.
- `dma_read`: a `$DE00-$DFFF` read that no SID decodes goes to TRX64's bus and then updates the cartridge lines
  (`cart_changed`). The SID stream's version returned before that step, which would drop read-triggered mode changes
  (KCS, Epyx, Westermann, …) on DMA reads.
- `advance_to` runs `run_cpu`, then the drive's written-track check, then `Sid::advance`. `set_reset` keeps the
  drive's hooks around `Machine::warm_reset` and the SID's reset and re-anchor.
- `C64Port` has 10 windows (EEPROM and drive A added). The drive A register accesses lend DDR around their C64 sync
  and return it before `DriveRegs` uses `IoCtx::ram`; `tick` does the same before the drive write-back.
- `runner::attach_trx64` applies the SID options and audio sink and sets CAPAB_EEPROM.

## A blank flash has no C64 ROMs

On a blank `--flash` the C64 shows the firmware's placeholder KERNAL:

```
  Welcome to the Ultimate-64 Elite-II!

 To avoid any potential legal issues,
 the Ultimate-64 is shipped without
 System ROMs. […]
```

`init_system_roms` finds no `/flash/roms/kernal.bin` ("Failed to load KERNAL ROM; loading default.") and uploads
`_default_kernal_65_start` (u64ii/default_kernal.tas; c64.cc:1091-1096). The factory prep app writes no C64 ROMs either
(flash_disk_prep.cc:93-95 are commented out), so hardware starts the same way. The bridge's seeds from `--roms`
(S14 §5.5) are overwritten by that upload.

### `--c64-roms`: ROMs into the flash image before boot

`ue2emu run --flash run/flash.bin --c64-roms [DIR]` replaces the menu steps. Before the machine opens the image, it
writes the KERNAL, BASIC and CHAR ROMs into `/flash/roms` (crates/ue2emu/src/c64roms.rs). The first boot then reaches
BASIC `READY.`. `ue2emu install --c64-roms` does the same after the updater, because the updater reformats a `/flash`
that holds files (update_common.h:228-257). Each action is logged on stderr as `c64-roms: …`.

- **Sources.** DIR defaults to `--roms`. The flag takes the first file with the right size: `kernal.901227-03.bin` or
  `kernal.bin` (8192 bytes), `basic.901226-01.bin` or `basic.bin` (8192), `characters.901225-01.bin` or `chars.bin`
  (4096). The firmware tree's `chars.bin` is the 2K overlay font, so its size rules it out. A file that does not start
  the way "Set as … ROM" expects (filetype_bin.cc:162-194) is used with a warning.
- **Names.** `init_system_roms` loads the names that "C64 and Cartridge Settings" selects: items 0xE1-0xE3
  (c64.h:232-234), at most 30 characters (config.cc:693-699), with defaults `kernal.bin`, `basic.bin`, `chars.bin`
  (c64.cc:84-86).
  - The store is read from the first config page with id 0x43363420, else from `/flash/config/page_43363420.bin`
    (config.cc:127-152). Without either, the defaults apply.
  - "Set as … ROM" copies the file under its own name and stores that name (filetype_bin.cc:166-199,
    c64.cc:283-297). Writing under the selected names therefore gives the same result, and the config is never
    written. An empty name (list_basics/list_chars offer one) is left alone.
- **Volume.** `/flash` is an MBR-less FAT volume at 0x580000, 2664 × 4 KiB (FPGA type 3; 0x400000, 3048 × 4 KiB
  otherwise, w25q_flash.cc:51-63).
  - An erased region is formatted first, exactly as `format_flash` would: `f_mkfs` with `FM_SFD | FM_ANY`, one FAT,
    512 root entries on 4096-byte sectors, 1-sector erase block (filesystem_fat.cc:107-120,
    blockdev_flash.cc:115-146, ff.c:6197-6354).
  - The result is FAT12 with 1 reserved sector, 1 FAT sector, 4 root directory sectors and 2658 one-sector clusters,
    OEM `MSDOS5.0`, `NO NAME`, `FAT     `, serial = `get_fattime()`. The 50T layout gets 2 FAT sectors and 3041
    clusters.
  - The firmware mounts this volume instead of formatting at boot (blockdev_flash.cc:170-178).
  - A region that is neither a FAT volume nor erased is refused, and nothing is written.
- **Existing files.** Same content: unchanged. Other content: kept, unless `--c64-roms-force`. Only changed 4 KiB
  sectors are written, so a repeated run leaves the image byte for byte as it was.
- **Needs `--flash`.** A volatile flash has no image to write to.

## Performance (A6)

M2 (`wait 60000`, `--log unmapped`), same host, one run at a time. MIPS is the last 500 ms interval, so wall time is
the steadier number.

| Build / option | Host MIPS | Wall | Peak RSS |
|---|---|---|---|
| `--c64 trx64` (default: TRX64 rings off) ×2 | 125, 125 | 12.17 s, 11.95 s | 67.0 MB |
| `--c64 trx64`, `TRX64_CPUHISTORY=1` (rings on) | 123 | 12.31 s | 169.5 MB |
| `--c64 none` ×4 | 212, 207, 214, 213 (median 212.5) | 7.21-7.28 s | 62.8 MB |
| pre-S14 `d51fa61` ×4 | 202, 202, 201, 202 (median 202) | 7.60-7.83 s | 62.7 MB |

- **`--c64 trx64`:** 60 s emulated in 12 s wall is 5.0× realtime, as predicted (1/(1/8 + 1/13.6)). 125 host MIPS
  (≥ 100), 12.2 s (≤ 15 s), RSS +4 MB over `--c64 none` (≤ 60 MB).
- **Reverse rings:** switched off but left at TRX64's default depth they still cost 112 MB RSS (first measurement:
  177.8 MB, 128 MIPS), because `Machine::new` allocates them before any switch applies. The bridge therefore sets
  `TRX64_REVERSE_SECONDS=1` and swaps in one-entry rings when it switches them off. With `TRX64_CPUHISTORY=1` they
  run: +103 MB, about 2 % fewer MIPS.
- **`--c64 none`** is not slower than the pre-S14 commit: median 212.5 vs 202 MIPS, 7.2 s vs 7.6 s wall. The T0 path
  only changed where the C64 windows are decoded (one device through `IoMap::map_origin` instead of three).

**Realtime.** `--speed realtime --flash run/flash.bin` (ROMs installed, BASIC idle) with `wait 60000` then `c64screen`,
headless: 60.004 s emulated in 60.02 s wall, 25 MIPS, 17.9 s CPU, 70 MB RSS, and the dump shows `READY.`. Over the
whole run, boot included, emulation stayed within 16 ms of the wall clock. The pacer's per-slice lag is not logged, and
the window variant was not run by the agent.

## Known gaps

- **PAL only.** The firmware defaults to System Mode NTSC; the C64 runs PAL (TRX64's VIC is 6569 only). Program timing
  and the 50/60 Hz assumptions of overlay and resampler differ from hardware.
- **Stops and DMA land on instruction boundaries.** STOP_MODE is latched only; HAS_STOPPED is immediate for every mode,
  so `stop(true)` always reports "Frozen on Bad line". Raster-timed programs may glitch on freeze/resume.
- **Cartridges** (`docs/status/carts.md`): REU, ACIA, the sampler, C128 carts and the types the firmware rejects are
  not modelled. UCI is modelled since S15, in TRX64. KCS, SS5 and FC1 freezing, GeoRAM and TwoMegabyter were not run
  from the firmware; Business Basic's dynamic mode is off.
- **SID** (`docs/status/sid-audio.md`): one reSID for socket 1 and UltiSID 1. Socket 2, UltiSID 2, stereo, mixer
  gains, VOICE_ADSR and the UltiSID filter curves are not modelled, and C64 programs read TRX64's fastsid registers.
  Socket 1 is empty by default, because a fitted ARMSID makes a fresh flash ask to review the SID settings.
- **Drives** (`docs/status/drive.md`): drive A is a 1541 only (no 1571/1581, no MFM). Drive B has registers only,
  and the IEC processor (SoftIEC, printer, UltiCopy) stays T0.
- **RSS:** linking cpal (CoreAudio, AudioUnit) adds about 20 MB peak RSS, audio on or off.
- **ITU IRQ bit 7** (C64 reset event) and **high IRQ 6** (unlock) are raised since S15, from the UCI block's events
  (`docs/specs/S15-uci.md` §3.3). High IRQ 6 is dropped again by the handler's own `C64_POKE(0xD038, 0)`, because the
  ITU has no ack register; whether that is the real source on hardware is S15 open question 6.
- **Keyboard ownership** is a guess (05 OQ6): host key-downs do not reach CIA1 while overlay TRANSPARENCY bit 6 is set.
  MATRIX_KEYB [8] reset is latched only ([10] is the cartridge freeze button since W4-CART); the joystick swap bit is ignored.
- **`type` and the C64:** the control language uses the firmware keymap, where an upper-case letter is SHIFT + key; on
  the C64 that is a graphics character, so BASIC is typed in lower case.
- **`c64screen`** guesses the text encoding from the VIC character base: ROM upper/lower case as screen codes, any RAM
  font as the Freeze UI's ASCII. A program with its own font dumps as ASCII.
- **Window:** the realtime pacing with the C64 attached was checked headless only (below); the window itself was not
  started by the agent. Page Up is RESTORE.
- **TRX64 pin:** a moved TRX64 checkout fails the build until c64-bridge is re-checked against it.

## UCI (S15)

The Ultimate Command Interface works. The block itself is TRX64's, on its `u64` machine profile (TRX64 Spec 852, on
the expansion-port interface of Spec 850 and the profile of Spec 851); UE2 maps the firmware window 0x10044000 onto
it, drives the ITU bits, and routes it. Design and the division of labour: `docs/specs/S15-uci.md`.

What changed here, in one line each:

- The bridge builds the machine with `set_machine_profile(SpeedProfile::U64)` before the power-on reset, so the C64
  is an Ultimate and brings the UCI block with it.
- `C64Backend` gained five defaulted UCI methods and a `UciEvents`; `C64Port` gained the 0x10044000 window. The T0
  register table moved out of `devices/iec.rs` into `devices/c64.rs` and now answers only without a block.
- ITU low bit 4 follows the block's firmware IRQ as a level, low bit 7 pulses on its C64-reset event, high IRQ 6 is
  set on its unlock event and dropped by the handler's `C64_POKE(0xD038, 0)`.
- The bridge's own `run_chips` loop is gone: `Machine::set_hold(Hold::Cpu)` for C64_STOP, `Hold::Reset` for the held
  reset. The cartridges' IRQ/NMI moved off the RESTORE source onto `set_expansion_lines`.
- C64_BUS_INTERNAL bits 0/1 drive `Uci::set_routed`; the C64_SPEED_UPDATE strobe applies the latched
  C64_TURBOREGS_EN / C64_SPEED_PREFER through `set_u64_turbo`.

### Caveats of this run

- **A5 on a freshly seeded flash: no difference, checked against a pre-S15 binary.** The earlier doubt came from a
  run without `--no-overlay-ui`, which the script's header requires. With it, `--flash <fresh> --c64-roms
  --no-overlay-ui --usb-keyboard` gives the same result before and after this change (release binary of `614021f`
  vs `57c82eb`): exit 0, one `Frozen on Bad line. Raster = 01`, no `Hard stop!!!`, three `State *Root* reloaded`
  and the Freeze UI menu in the second dump.
- The C64 smokes that dump after a fixed `wait 6000` (`ready`, `sid-tone`) need the C64 to have reached BASIC by
  then. On a heavier flash it has not, and the dump is garbage while the run still exits 0, because those two
  scripts carry no `expect`. Read the greps, not the exit code.
- The runs above used copies of existing flash and SD images in a temporary directory, not the repo's `run/`.
