**Changes against the design, found while building** (the sections below are updated):
- `set_reset` takes no DDR: `C64Port` calls `set_cart(type, DDR)` right before a release (§3, §5.1).
- TRX64's reset zeroes `c64_core.clk` (c64_6510core.rs:677), so the bridge re-anchors its clock after every release (§4, §7).
- The CHAR seed is `characters.901225-01.bin`; `chars.bin` is the 2 K overlay font (§5.5).
- A blank flash never reaches BASIC READY, seed or not: `init_system_roms` falls back to the firmware's *placeholder* KERNAL, a "shipped without system ROMs" welcome screen (u64ii/default_kernal.tas; c64.cc:1091-1096). Hardware does the same: the factory prep writes no C64 ROMs (flash_disk_prep.cc:93-95, commented out). A2 first installs the ROMs through the firmware's own "Set as … ROM" actions (filetype_bin.cc:78-95, 148-195), `scripts/smoke-c64-roms.ctl` (§5.5, §12).
- The NORMAL cart kill needs `$DFFF` bits 7:6 = 01, and the reset line re-enables the cart (all_carts_v5.vhd `c_normal`, `cart_en <= reset_in`); variant bit 0 drives EXROM, bit 1 GAME (§8).
- JOY1/2_SWOUT power on released (0xFF); a RAM latch of 0 would hold every joystick line and pull keyboard rows low (§5.3).
- `c64_text_dump` reads the screen per character set (`C64Frame.charset`): the Freeze UI draws ASCII with its own font at $0800, which the screen-code mapping turns into `#` (§9, A5).
- A3 types `print 6*7`: in the firmware keymap an upper-case letter is SHIFT + key, which the C64 prints as graphics (§12).
- build.rs of c64-bridge failed the build unless TRX64 was at `a448229` (risk "TRX64 keeps changing"). That check is gone: `trx64-core` is now a git dependency pinned in `crates/c64-bridge/Cargo.toml`. The window opens at 768×576 so the 384×272 frame shows at 2×; Page Up is RESTORE.

## 1. Goal and phase A scope

Replace the T0 C64 stub (`crates/ue2-core/src/devices/c64.rs`, doc 10 §T0) with a real, cycle-exact C64: TRX64 `trx64-core::Machine`. The unmodified firmware must be able to:

- reset, stop and resume it;
- upload KERNAL, BASIC and CHAR ROMs into it;
- read and write its bus through the DMA window;
- start the internal boot cartridge, so a PRG runs from the file browser;
- draw the Freeze UI on its screen.

Its video appears in the window and in PNGs, under the overlay.

**Phase A includes:**
- cart/machine control (MODE, STOP, STOP_MODE, CLOCK_DETECT, CARTRIDGE_TYPE/KILL/ACTIVE);
- the DMA window with DMA_MEMONLY and the ULTIMAX lens;
- ROM windows, the C64 palette and the C64 core config latches;
- MATRIX_KEYB and host keys into CIA1, host joystick into port 2, JOY SWOUT;
- the NMI line;
- the video frame and a C64 screen text dump;
- the **CART_TYPE_NORMAL family only** (`0x01` variants; the boot cart is `0x41`). Without it the PRG-run acceptance cannot pass (doc 10 H18/H19).

**Phase A excludes** CRT mapper families, UCI, REU, EEPROM, drive A/IEC, SID audio and addressing, NTSC, turbo, paddles/mouse, and the bad-line/R-W stop conditions (§11).

**Why a trait in ue2-core, with the cargo feature on ue2emu only:**
- `trx64-core` compiles vendored reSID C++ in `build.rs` and brings serde, flate2, sha2 and base64 (`Cargo.toml`, `build.rs`).
- ue2-core has 192 tests and a T0 path. They must keep building with no C++ toolchain and no TRX64 checkout.
- The trait lets `C64Port` be unit-tested in ue2-core with a mock backend.
- `cargo test -p ue2-core` never builds TRX64.
- `--no-default-features` builds a T0-only ue2emu.
- Licences match: both are GPL-3.0-or-later (`Cargo.toml` of both workspaces).
- The path dependency resolves `edition.workspace = true` against TRX64's own workspace root and builds into ue2's `target/`, so the TRX64 tree is not modified. (Since replaced by the git dependency; a local checkout is patched in as docs/status/install.md, "TRX64 dependency", describes.)

**Why one device through `IoMap::map_origin`:**
- `IoMap::resolve` hands a device `addr - window.base` (io.rs:111-125), so a device mapped at several windows cannot tell them apart. That is why the stub is split into `CartRegs`, `DmaWindow` and tables.
- Additive: `map_origin(base, size, dev, origin)` pushes `Window { base: origin, dev }` but marks the grains of `base..base+size`. Resolve is unchanged; `map()` becomes `map_origin(base, size, dev, base)`.
- `C64Port` is installed with origin `0x10000000` over the windows in §5, so offsets are absolute minus `IO_BASE`.
- The rejected alternative is several devices sharing `Rc<RefCell<backend>>`. It is legal, because the machine is built on the emulation thread (runner.rs:124-129), but it splits one state machine (STOP, MODE, cart) across devices.

    fn rom_read(&self, rom: C64Rom, off: u16) -> u8;

## 4. Time sync

- **Clocks.** The emulated clock is 100 MHz (time.rs:3). The C64 runs from the PAL master clock, 985 248 Hz (0.6 ppm drift against 17 734 475/18 is ignored).
  - `cycles(now) = now × 985 248 / 100 000 000`, computed in u128 from the attach clock.
  - 1 C64 cycle = 101.497 clocks, which is 25.4 RV32 instructions at 4 clocks per instruction.
  - 1 PAL frame = 19 656 cycles ≈ 19.95 ms.
- **Stepping.** The backend keeps `target = cycles(now)` and runs until `c64_core.clk >= target`.
  - It calls `Machine::run_for_full_capped(target - clk, u64::MAX, &mut NullSink, |..| {})` (lib.rs:1991), which steps whole 6510 instructions (lib.rs:2017-2080).
  - Overshoot (at most about 7 cycles plus a BA steal) is carried: the next call starts from the real `clk`.
  - DMA accesses therefore land on instruction boundaries. Real hardware lands on cycles; the firmware cannot observe the difference because it always stops first (u64_machine.cc:152-177).
- **When the C64 advances.** The C64 never runs ahead of the RV32.
  - **Periodic:** `C64Port::next_event() = synced + 100 000` (1 ms, about 985 cycles). `Machine::pre_step` ticks it (machine.rs:248-252; bus.rs:130-144).
  - **Lazy:** every `read8`/`write8` on the cart registers `0x00`-`0x0F`, the DMA window or MATRIX_KEYB first calls `advance_to(ctx.now)`, so polls see C64 state at the exact RV32 instant (C16 `$D012`, H19 `$0002`, H18 ACTIVE).
- **STOP.** Only the 6510 is held; VIC, CIAs and SID keep running (doc 10 §Stop/DMA; c64.cc:548-566 reads a live raster while stopped). While `stopped`, `advance_to` runs **chips only**, per cycle:
  - `vic.tick(&VicMemView { ram, char_rom: Some(char_rom), color_ram: &io_shadow[0x800..0xC00], vbank: vic_bank_base() })`, which also draws the pixels (vic.rs:1324, 1375);
  - then `c64_core.clk += 1` and `cia1/cia2.tick` with their `clk` set to it;
  - after the batch `cia1/cia2.update_to(clk)` (cia.rs:710), `sid.tick(n)` and `machine.clk = c64_core.clk`, which `read_full_live`/`write_full` use as "now".

  Since S15 this loop is TRX64's, not the bridge's: `Machine::set_hold(Hold::Cpu)` and the run loop's `run_held`
  (Spec 850 D7, which took the bridge's `run_chips` in). API gap 1 is closed. What the bridge still does around it is
  the Epyx capacitor hold time and drive A, because `Hold::Reset` deliberately leaves the drive standing while the
  U64's drive registers decide for themselves (RESET bit 1 `use_c64_reset`). It is **required**:
  - `DetectSidImpl` polls `$D012` for 0xFF with interrupts masked while hard-stopped (u64_config.cc:2239, 00 §2 C16);
  - the Freeze UI is only visible if the VIC keeps drawing while the CPU is held for the whole menu session (c64.cc:985-1008).

  CIA interrupts that latch are taken on resume, at the next boundary refresh (lib.rs:2078-2082).
- **Reset held** (MODE bit 2): only the VIC is ticked; CPU, CIAs and SID are frozen.
- **Pacing:** unchanged. `Speed::Realtime` paces on RV32 emulated time, and the C64 follows it.

## 5. Register mapping (`C64Port`; ue2 citations are to the current stub)

### 5.1 Cart/machine control `0x10040000` (decode `addr & 0xF`, repeats over 0x100)

| Off | FW use | Phase A behaviour |
|---|---|---|
| 0x00 MODE | W: bit 2 reset, else bit 3 release, else bits 1/4 (c64.h:70-73; cart_slot_registers.vhd) | Keep the stub's latch rules (c64.rs `write8`). Sync first. Reset edge 0→1: `set_reset(true)`. Release while held: `set_cart(TYPE, DDR)`, then `set_reset(false)`. Bit 1 change: `set_ultimax`. Bit 4: NMI level OR MATRIX_KEYB[9] OR host RESTORE. R = latch (H16) |
| 0x01 STOP | W bit 0 request; R bit 0 req, bit 1 HAS_STOPPED (c64.h:84-85) | Sync first, then `set_stopped(bit0)`. **HAS_STOPPED = request, immediately, for every STOP_MODE** (hard_stop's unbounded poll c64.cc:399-409, 00 §2 C12). R = `req \| req<<1` |
| 0x02 STOP_MODE | 0 bad line, 1 R/W sequence, 2 force (c64.h:77-79) | Latch only in phase A. `stop(true)` then reports "Frozen on Bad line" and takes the stop_mode 1 resume path (c64.cc:437-456, 524-597), which works with a live raster |
| 0x03 CLOCK_DETECT | bit 0 PHI2, bit 4 RESET sense (c64.h:88-93; H4, H8) | R = `0x01 \| (reset_held << 4)` with a backend; 0x01 as in T0 without |
| 0x05 CARTRIDGE_TYPE | type\|variant (c64.h:115-163); written before the ROM copy (c64.cc:1281-1288) | Latch. Mapper (re)built from DDR at reset release and on the KILL bit 1 strobe (§8) |
| 0x06 KILL/ACTIVE | W bit 0 kill, bit 1 force ×2 (c64.cc:1469-1474); R bit 0 active (c64_subsys.cc:180-191) | W bit 0: `kill_cart()`. W bit 1: `set_cart(type, ddr)`. R bit 0 = `cart_active()` |
| 0x07-0x0E | KERNAL_EN, REU, REU_SIZE, SWAP, TIMING, PHI2_REC, SERVE_CONTROL, SAMPLER | Latches exactly as today (c64.rs `CART_REGS`). SERVE_WHILE_STOPPED is a no-op, because TRX64's cart always answers the bus |

### 5.2 DMA window `0x10050000-0x1005FFFF` (doc 10 §DMA)

Every access syncs first.

| Case | Read | Write |
|---|---|---|
| `C64_DMA_MEMONLY` (0x10180003) = 1 | `machine.ram[a]` (includes `$00/$01`: RAM under the port, OQ2) | `machine.ram[a] = v` (clear_ram `raminit.bin`, u64_machine.cc:349-373) |
| MEMONLY = 0, `$D400-$D7FF` | **0x00**: no SID sockets are modelled, so every detector reports "none" (H12/H13, u64_config.cc:572-640) | `write_full`, to TRX64's SID |
| MEMONLY = 0, other | `Machine::read_full_live(a)` (lib.rs:1198): the live PLA with `$01`, cart lines and forced ULTIMAX, with side effects (CIA ICR clear, filetype_sid.cc:715-716) | `Machine::write_full(a, v)` (lib.rs:1147), including `$00/$01` to the port latches (u64_machine.cc:37-56 dummy reads) |

- **ULTIMAX lens (MODE bit 1).**
  - The bridge installs `ForcedUltimax { cart: Option<NormalCart> }` as `machine.cartridge`, a bridge-side `CartMapper` (cart.rs:351-458). It keeps its own `NormalCart` and rebuilds the boxed mapper on every change, so nothing has to be downcast back out of TRX64.
  - Its `get_lines()` returns `exrom = 1, game = 0`. Read, peek and write delegate to the cart, or return `None` (open bus).
  - After every change the bridge sets `machine.memconfig = machine.memconfig_table[machine.pla_index()]` (lib.rs:827).
  - TRX64's ultimax memconfig gives exactly the freezer decode: RAM `$0000-$0FFF`, I/O always, open bus at `$1000-$7FFF` and `$A000-$CFFF`, cart windows at `$8000`/`$E000` (full.rs:84-151, 700-745; c64.cc:451-456).
- **Live DMA** while the C64 runs (OQ12: boot CIA pokes u64_config.cc:950-951, unlock ISR `$D038`): sync, then apply at the instruction boundary.

### 5.3 C64 core config `0x10180000-0x101800FF`

- RAM latches as today (c64.rs `CORE_CONFIG`, H16), `CORE_VERSION` constant, `VOICE_ADSR` reads 0.
- Functional in phase A:
  - `0x03` DMA_MEMONLY (§5.2);
  - `0x30`/`0x31` JOY1/2_SWOUT: active-low bits 4:0, ANDed into the ports (joystick_output.cc:81-82). They power on as 0xFF (released): the firmware writes them only for USB/REST joysticks, and a 0 would hold every direction and fire and pull keyboard rows low through port 1;
  - `0x01` VIDEOFORMAT: stored. If bit 1 (60 Hz) is set, log once "C64 core is PAL-only" (§12).
- Latched only: SID bases/masks/EN, BUS_*, TURBO/SPEED, PADDLE, VIC_SPLIT, SCANLINES, PHASE_INCR.

### 5.4 Palette `0x10180800-0x10180FFF`

- RGB at `+0x000..0x03F` goes to `set_palette_byte`. The firmware writes the same `default_colors` table it writes to `0x10145000` (u64_config.cc:2720-2743, 54-70).
- YUV at `+0x400` is ignored. Reads return 0, as today (the stub test `c30_core_config_latches`).
- Before the firmware writes, the palette is TRX64 `COLODORE` (render.rs:25).

### 5.5 ROM windows `0x10188000` BASIC / `0x1018A000` KERNAL / `0x1018C000` CHAR

- **Live.** Writes go straight into `machine.basic_rom`, `kernal_rom` and `char_rom` (lib.rs:440-522; used by FullBus and `warm_reset`'s vector fetch). The firmware rewrites them on every `init_system_roms` (c64.cc:1077-1109) and while running (`enable_kernal`, c64.cc:1399-1407).
- **Readable.** Reads return the array bytes (00 §1c M8; u64_machine.cc:92-107; u64_memory_backend.cc:74-83).
- **Seeding.** `init_system_roms` loads BASIC from `/flash/roms/basic.bin` **with no fallback** (c64.cc:1103; ROMS_DIRECTORY c64.h:12). KERNAL and CHAR fall back to images built into the firmware (c64.cc:1091-1108).
  - `Trx64Backend::new(rom_dir)` seeds `basic_rom` from `rom_dir/basic.bin`, `kernal_rom` from `kernal.901227-03.bin` and `char_rom` from `characters.901225-01.bin` when present (`chars.bin` there is the 2 K overlay font). `firmware/1541ultimate/roms` holds all three.
  - A firmware upload overwrites the seed; a failed BASIC `load_file` leaves the window as it was.
- **Blank flash.** The KERNAL fallback `_default_kernal_65_start` is a placeholder (u64ii/default_kernal.tas): the C64 shows "Welcome to the Ultimate-64 Elite-II! … shipped without System ROMs" and how to install them. The factory prep writes no C64 ROMs either (application/u64ii_prepare_fat/flash_disk_prep.cc:93-95, commented out), so real hardware starts the same way. The seeds therefore do not reach BASIC READY on a blank `--flash`; the ROMs have to be installed once with the browser's "Set as Kernal/Basic/Char ROM" actions, which copy the file to `/flash/roms` and set CFG_C64_KERNFILE/BASIFILE/CHARFILE (filetype_bin.cc:78-95, 148-195; c64.cc:281-299). Every later boot on that flash uploads them (§12 A2).

### 5.6 MATRIX_KEYB `0x10100300-0x101003FF` (moved from board.rs:212-214)

- Stays RAM with read-back, including the unaligned 32-bit write at `0x30B` (00 §2 C19; test `c19_matrix_wasd_32bit_store` moves with it).
- After a write to `[0..7]`: `set_matrix_keyb(rows)`, active-high, byte a bit b = key (a, b) (keyboard_usb.cc:214-229; 05 §D).
- `[9]` restore is ORed into NMI. `[8]` reset and `[10]` freeze are latched only (05 OQ7).

## 6. Keyboard and joystick

- **Key position convention.** ue2 `set_key(row, col)` uses `row` = the bit driven on U64II_KEYB_COL (CIA1 PA) and `col` = the bit read on ROW (CIA1 PB), with index `row*8+col` (u64io.rs:73-94). TRX64 `key_matrix` returns `(col, row)` with col = PA drive and row = PB read (keyboard.rs:18-47). The numbers are the same pair; only the names are swapped.
- **Name table.** `c64-bridge/keys.rs` holds a 64-entry table: index → TRX64 key name (e.g. (0,1) "RETURN", (1,7) "L_SHIFT", (7,7) "RUN_STOP", (6,6) "UP_ARROW").
- **Folding sources.** The bridge keeps its own pressed set: host keys OR MATRIX_KEYB. On each change it calls `keyboard.key_down/key_up(name)` (keyboard.rs:170-182). `cia1_pa_pins`/`cia1_pb_pins` (keyboard.rs:322-350) then serve both CPU reads and DMA reads (freeze scan: `Keyboard_C64(this, &CIA1_DPB, &CIA1_DPA, &CIA1_DPA)`, c64.cc:143; boot hotkey keyboard_c64.cc:135-138, stays stable 0xFF when idle, C18).
- **After reset.** `cold_reset` clears the keyboard and joysticks (lib.rs:973-1036), so the bridge re-applies its pressed set after every `warm_reset`.
- **Joystick.** Host joystick bits 0-4 (up, down, left, right, fire, active low) go to `machine.joystick2` (keyboard.rs:270-290), ANDed with JOY2_SWOUT; port 1 is JOY1_SWOUT alone. The joystick swap bit (0x10100406 W) is ignored in phase A.
- **RESTORE.** `HostInput::Restore` plus MODE bit 4 plus MATRIX_KEYB[9] → `c64_int.set_nmi(INT_SRC_RESTORE, level, clk)` (c64_6510core.rs:155, 306). The run loop refreshes only sources 0-2, so source 3 persists.

## 7. Reset and power-on

- **Power-on.**
  - Set `TRX64_CPUHISTORY=0` if unset, before `Machine::new()`. This turns off the always-on reverse rings: cpu_history.rs:98, delta_ring.rs:28 (about 96 MB at the 10 s default), plus a per-instruction recording cost.
  - Then `fill_power_on_ram()` (lib.rs:814), seed ROMs (§5.5), `full_assembled = true`, `cold_reset()`.
  - The initial MODE/STOP state is unknown (doc 10 OQ1); the firmware sets both (c64.cc:147-148, u64_config.cc:914).
- **Reset release** (MODE bit 3 while bit 2 held, or `C64::reset` c64.cc:615-623):
  1. rebuild the cart from DDR (`set_cart`, called by `C64Port`);
  2. re-apply ultimax;
  3. `machine.warm_reset()` (lib.rs:1054): RAM kept, CPU/CIA/VIC/SID reset, `$FFFC` read through the live KERNAL/cart map;
  4. re-anchor the clock at the release instant, because the reset zeroes `c64_core.clk` (c64_6510core.rs:677);
  5. re-apply keys and joysticks. A held NMI is not re-asserted: the 6510 needs a new edge.
- **Boot order this serves:**
  1. U64Config: `hard_stop` → SID detect (chips-only raster) → `clear_ram` (MEMONLY 64 KB) → resume (u64_config.cc:914-941).
  2. `c64->init()`: `init_system_roms` → `init_cartridge` (MODE←RESET because STOP==0, TYPE←0, KILL←2 ×2, MODE←UNRESET, STOP←0) (c64.cc:1444-1478).
  3. Warm reset → KERNAL boot → `READY.` about 3 s emulated later.
- **ITU IRQ bit 7** (reset event, doc 10 OQ3) is not raised, as in T0.

## 8. Boot cartridge subset (CART_TYPE_NORMAL family)

- **Mapper.** `c64-bridge/cart.rs` `NormalCart` implements `CartMapper`, built from a copy of DDR `0x03C00000`-`0x03C03FFF` (linker.x:269-287; `set_cartridge` memcpy c64.cc:1285-1288). As in all_carts_v5.vhd `c_normal`, variant bit 0 drives EXROM and bit 1 GAME (active low); ROML is +0 and ROMH +0x2000 for both `$A000` and `$E000` (`rom_mode "01"`), and TRX64's PLA only asks for the windows the lines map:
  - variant 2 `0x41` 8K (`CART_TYPE_8K`, c64.h:154): ROML `$8000-$9FFF`, exrom 0, game 1;
  - variant 0 `0x01` 16K: adds ROMH `$A000`;
  - variants 1/5 `0x21`/`0xA1` ultimax: ROMH `$E000`;
  - variant 3 `0x61`: lines 1/1, off.
- **Kill.** A write to `$DFFF` with bits 7:6 = 01 disables the mapper until the next reset (lines 1/1, `cart_active = false`; `cart_en <= '0'` in `c_normal`; the boot cart writes $40, bootcrt.tas:86-89, 591, 609). The write is consumed, so FullBus re-runs the PLA (full.rs io_write `$DE00-$DFFF`). The kill flag is an `Arc<AtomicBool>` shared by the bridge's copy and the one TRX64 holds; `CartMapper::reset` sets it again (`cart_en <= reset_in`).
- **Other types.** TYPE 0 means no mapper. Any other type logs once "cart type %02x: phase B", attaches no mapper, and reads ACTIVE = 0.
- **What this unlocks.** `dma_load` (c64_subsys.cc:591-671): `$0002`←0x80 → `start_cartridge(boot_cart)` → the boot cart code writes `$0002`=1 → the firmware DMA-loads the PRG → the `$0150` runner kills the cart and `RUN`s → `restoreCart` sees ACTIVE=0 (c64_subsys.cc:178-192, H18/H19).

## 9. Video

- **Capture.** On `frame()`, `render_canvas_indices()` (lib.rs:1766) gives 384×272 colour indices of the last complete frame (render.rs:83-86; `displayed` is swapped at start of frame, vic.rs:1265-1271). The firmware palette goes into `C64Frame.palette`.
- **Screen codes.** `screen` = 1000 bytes of `ram[vic_bank_base() + (($D018 >> 4) << 10)]` (lib.rs:1742).
- **Cost.** Captured only at snapshot publish, every 20 emulated ms (runner.rs:22, 213-215); about 105 KB per snapshot.
- **`render.rs` composite.** When `snap.c64` is Some:
  - canvas = max(C64 size, overlay grid);
  - the C64 is palettized and centred;
  - the overlay grid is centred on top, X_ON/Y_ON ignored (05 OQ4);
  - hidden-overlay and transparent-index pixels show the C64 instead of `BACKDROP` (05 §B, OQ3).

  `snap.c64 == None` gives today's output byte for byte. `window.rs:137-150` and `control.rs png` go through the same `Renderer::render`.
- **`render::c64_text_dump(&snap)`.** One line per row, 25 rows × 40, trailing spaces trimmed, bit 7 ignored. The mapping follows `C64Frame.charset`, taken from the character base `vic_bank_base() + ((($D018 & 0x0E)) << 10)` (CHAR ROM at $1000-$1FFF of banks 0/2, vic.rs:149-157):
  - `Upper` ($1000): 0x00 '@', 0x01-0x1A 'A'-'Z', 0x1B-0x1F `[\]^_`, 0x20-0x3F as ASCII, 0x40-0x7F '#';
  - `Lower` ($1800): 0x01-0x1A 'a'-'z', 0x41-0x5A 'A'-'Z', the rest as `Upper`;
  - `Ram` (any other base): the Freeze UI copies `chars.bin` to $0800 and writes ASCII (c64.cc:916-926, 961), so it reads like the overlay `text_dump`: 0x20-0x7E as ASCII, 0x00-0x1F line graphics.
- **New control command `c64screen`** prints the dump between `--- c64 ---` markers (control.rs:6-14 table).

## 10. What stays T0

Legacy SID `0x10042000`, CART_TIMING, sampler, PLD, U64 debug, glyph, UltiSID filter RAM and UDP headers keep their `add_table` stubs (c64.rs `install`). ## 11. Phase B outline

Wave 4 did the cartridges (§W4-CART), drive A without the IEC processor (§W4-DRIVE) and the SID without VOICE_ADSR and mixer gains (§W4-SID). UCI, exact stops, NTSC and the rest below are open.

- **Cartridges.** U64 TYPE/variant (c64.h:115-163) → TRX64 families (`MapperType` cart.rs:39: Ocean, MagicDesk, EasyFlash, GMod2 with the `0x1004C000` EEPROM, MegaByter…), fed from `C64_CRT` DDR placement (c64_crt.cc:291-358). Also KILL/force semantics (OQ8), BUS_INTERNAL/EXTERNAL, ITU bit 7 on reset (OQ3), high IRQ 6 unlock (OQ4).
- **UCI** `$DF1C` (CMD_IF `0x10044000`, doc 11): **done, and not the way this line planned it.** The block is C64 hardware and lives in TRX64 (its Spec 852, on the expansion-port interface of Spec 850 and the `u64` profile of Spec 851); UE2 maps the firmware window onto it and drives the ITU bits. No bridge `CartMapper` composite, no shared RAM with iec.rs. See `docs/specs/S15-uci.md`.
- **Drive A / IEC:** TRX64 `Drive1541` (drive.rs:390) with the firmware-uploaded drive ROM and GCR track buffers per doc 11 §Drive "what the external 1541 emulator must share"; the IEC processor `0x10028000` on TRX64 `IecCore` (iec.rs:245). REU and 1571/1581 remain dropped (S11-S14-later scope).
- **SID:** DMA/CPU decode per SIDx_BASE/MASK (u64_config.cc:218-235); reSID audio (resid_audio.rs) to a host audio sink; VOICE_ADSR from envelopes; mixer gains.
- **Exact stops:** STOP_MODE 0/1 (bad line, R/W sequence; slot_master_v4.vhd:100-152) at cycle granularity, if TRX64 grows a hold hook.
- **Also:** NTSC core (VIDEOFORMAT, u64.h:163-170), turbo, paddles/mouse, joystick swap, cropper `0x10148000`, VIC/audio UDP streams, optionally the C64 on its own thread.

## W4-DRIVE — drive A as a 1541 on TRX64's drive 8

**Status:** built; results, numbers and gaps in `docs/status/drive.md`. The firmware stays the owner of image formats:
it converts D64/G64 to GCR in DDR and saves written tracks back; the emulator only moves GCR bytes between that DDR
and the drive (docs/hw/11 §Drive "what the external 1541 emulator must share").

**Changes against §1/§11:** drive A/IEC moves from "excluded" to built for the 1541 GCR path. 1571/1581, the WD177x
path, the IEC processor (0x10028000) and drive B stay T0.

### Interface (`ue2-core/src/c64host.rs`, additive)

```rust
pub const DRIVE_HALF_TRACKS: usize = 84;                  // floppy_stream.vhd track_i 0..83
pub struct DriveLines { power, reset, follow_c64_reset, stop_on_freeze: bool, device: u8, write_protect: bool, drive_type: u8 }
pub struct DriveStatus { half_track: u8, motor: bool, writing: bool, led: bool }
pub trait C64Drive {
    fn set_lines(&mut self, lines: DriveLines, rom: &[u8]);  // rom = DDR 0x00EE8000..0x00EF0000 (32 K)
    fn set_track(&mut self, half_track: u8, gcr: &[u8]);     // side 0
    fn track(&self, half_track: u8) -> &[u8];
    fn take_written(&mut self) -> u128;                       // bit n = half-track n
    fn status(&self) -> DriveStatus;
    fn read_ram(&self, out: &mut [u8]);                       // $0000-$07FF
}
// C64Backend gains: fn drive(&mut self, unit: u8) -> Option<&mut dyn C64Drive> { None }
```

### Registers (`devices/drives.rs` `DriveRegs`)

- **Window.** Drive A (0x10020000-0x10023FFF) is a `C64Port` window (`map_origin`, offset 0x20000): every access
  syncs the C64 first and reaches `C64Backend::drive(0)`; `C64Port::tick` (1 ms) syncs the disk. Without a backend,
  and for drive B (its own device), no drive is behind the registers, which reads as T0.
- **Registers** (decode bits 3:0 over 0x000-0x7FF, drive_registers.vhd): latches with the VHDL masks and reset values;
  SIDE 0; TRACK = drive half-track; STATUS = motor | writing << 1 (both gated by POWER, mm_drive_cpu.vhd:743-744) |
  write busy << 2 (2047 ms after the last observed write or a MAN_WRITE pulse; a RESET bit 0 write clears it). Writes to
  POWER, RESET, HW_ADDR, SENSOR and DRIVETYPE call `set_lines` with the drive area's ROM image.
- **DIRTY** (floppy.vhd:148-189): read = any_dirty << 7 | bit[off & 0x7F]; write bit 7 set clears any_dirty, else the
  addressed bit. Both sync the disk first.
- **Param RAM:** the 512 words are kept (reads 0); a byte write marks its side-0 half-track stale.
- **Disk sync:** stale half-tracks get `set_track(DDR[start .. start + max_offset + 1])` (word 0 bits 25:0, word 1 bits
  13:0; the bit time is not used). Each half-track in `take_written` is compared with DDR and copied back; its DIRTY bit
  (half-track >> 1) and any_dirty are set when the bytes changed or when the drive writes with the motor on under that
  head. Without INSERTED and a lit SENSOR (floppy_stream.vhd `do_write`) the drive's copy is reset from DDR instead.
- **Drive RAM** is copied to DDR 0x00EE0000 on every tick while powered (the firmware reads $78, c1541.cc:384-389).

### Bridge (`c64-bridge/src/drive.rs` `DriveA`)

- **Held drive.** The reset line is RESET bit 0, or bit 1 with the C64's reset held (c1541_timing.vhd). The CPU is
  clocked with POWER, drive type 1541 and not (bit 2 and C64 stopped). While not clocked or in reset, the real
  `Drive1541` is swapped out of `Machine::drive8` for a stand-in whose power-on reset has run and whose CPU clock is
  parked at 2^62, so TRX64's per-instruction catch-up executes nothing and the real drive's clock stands still. A reset
  release starts it from its ROM: `cold_reset`, head at half-track 0 (floppy_stream.vhd), surface re-attached.
- **Bus.** POWER (and type 1541) sets TRX64's IEC status bits TRUEDRIVE and DRIVETYPE for unit 8: on = callback Conf1,
  off = Conf0, where the C64 reads only its own lines (mm_drive_cpu.vhd:747-750). Rejoining re-derives `cpu_bus` from
  CIA2's output. Re-applied after every C64 reset (`Machine::cold_reset` builds a new `IecCore`).
- **C64 reset.** `Trx64Backend::set_reset` swaps the real drive out around `Machine::warm_reset` (which would reset
  drive 8 and drop its surface), then the lines decide.
- **C64 held.** `run_chips` clocks drive 8 as TRX64's run loop does, so a drive that runs while the C64 is frozen
  (the mount sequence clears RESET bit 2, c1541.cc:572, 605) sees time pass, and a stopped C64 no longer makes the drive
  fast-forward on resume.
- **ROM.** The upper 16 K of the image goes through a file in a private temporary directory into
  `Drive1541::load_rom` whenever it changes.
- **Surface.** `rotation.image` with the simple engine and no attach delay; `set_track` replaces one track and
  re-selects the track under the head.
- **Written tracks.** After each run: the half-track under the head while in write mode or with TRX64's dirty flag,
  TRX64's last written half-track when it changed, and the half-track the head stepped off.
- **Device number.** TRX64 wires the jumpers to device 8, so HW_ADDR n is patched into drive RAM $77/$78 once the DOS
  has set them to $28/$48 after a reset.

directory, `LOAD"TEST",8` + `RUN` prints `DRIVE A LOADED OK`, `SAVE"NEW",8` makes the firmware write tracks 19 and 18
back, and `scripts/d64tool.py` finds NEW in the SD image's `drive.d64` with the bytes of TEST. Unit tests: ue2-core
`devices::drives` (param RAM → surfaces, lines with ROM, writes → DDR/DIRTY/write busy, sensor gating, RAM mirror,
C28 through `C64Port`); c64-bridge `drive` (held/unpowered drive parked and off the bus, the 1541 DOS lists, loads and
saves a D64 surface, device jumpers).
